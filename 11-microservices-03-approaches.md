# Домашнее задание к занятию «Микросервисы: подходы»

Вы работаете в крупной компании, которая строит систему на основе микросервисной архитектуры.
Вам как DevOps-специалисту необходимо выдвинуть предложение по организации инфраструктуры для разработки и эксплуатации.


## Задача 1: Обеспечить разработку

Предложите решение для обеспечения процесса разработки: хранение исходного кода, непрерывная интеграция и непрерывная поставка. 
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- облачная система;
- система контроля версий Git;
- репозиторий на каждый сервис;
- запуск сборки по событию из системы контроля версий;
- запуск сборки по кнопке с указанием параметров;
- возможность привязать настройки к каждой сборке;
- возможность создания шаблонов для различных конфигураций сборок;
- возможность безопасного хранения секретных данных (пароли, ключи доступа);
- несколько конфигураций для сборки из одного репозитория;
- кастомные шаги при сборке;
- собственные докер-образы для сборки проектов;
- возможность развернуть агентов сборки на собственных серверах;
- возможность параллельного запуска нескольких сборок;
- возможность параллельного запуска тестов.

Обоснуйте свой выбор.

Предлагаемое решение: GitLab (Self-Managed в облаке или GitLab.com) + GitLab CI/CD + GitLab Runner (с кастомными агентами).

Это единая платформа (DevOps Platform), которая покрывает все требования без необходимости стыковать разнородные инструменты.


| Требование | Реализация в GitLab |
| :--- | :--- |
| **Облачная система** | `GitLab.com` (SaaS) или `GitLab Self-Managed` в вашем облаке (`AWS`, `Azure`, `GCP`, `VK Cloud`). |
| **Система контроля версий Git** | Встроенный Git-репозиторий. |
| **Репозиторий на каждый сервис** | Создается отдельный проект (repository) для каждого микросервиса. |
| **Запуск сборки по событию (Push/MR)** | Pipeline запускается автоматически по событиям `push`, `merge request`, `tag`. |
| **Запуск сборки по кнопке с параметрами** | Ручной запуск (`manual job`) с помощью директивы `when: manual` и использование `CI/CD Variables` для ввода параметров. |
| **Привязка настроек к каждой сборке** | Файл `.gitlab-ci.yml` в корне каждого репозитория. Возможность использовать блоки `variables` и `environment`. |
| **Шаблоны для конфигураций** | Использование ключевого слова `include` (внешние шаблоны из отдельного репозитория) и `extends` (наследование джобов). |
| **Безопасное хранение секретов** | Встроенное хранилище переменных (`Project/Group CI/CD Variables`) с маскированием (`masked`) и защитой (`protected`). Возможна интеграция с `HashiCorp Vault`. |
| **Несколько конфигураций из одного репозитория** | Использование правил (`rules`) и параллельных матриц (`parallel:matrix`) для запуска разных конфигураций (`dev`, `staging`, `prod`). |
| **Кастомные шаги при сборке** | Любые `bash`-скрипты или вызовы утилит прямо в секции `script` внутри `.gitlab-ci.yml`. |
| **Собственные Docker-образы для сборки** | Использование директивы `image:` для указания кастомного образа из любого Registry (в т.ч. встроенного `GitLab Container Registry`). |
| **Развернуть агентов на своих серверах** | `GitLab Runner` устанавливается на ваши сервера (`Linux`, `Windows`, `K8s`). Доступные типы исполнителей: `Docker`, `Shell`, `Kubernetes`. |
| **Параллельный запуск сборок** | Настройка параметра `concurrent` в файле `config.toml` раннера и создание пула из нескольких `GitLab Runner`. |
| **Parallelный запуск тестов** | Использование директивы `parallel:matrix` или разбивка тестов на независимые задачи (`jobs`), выполняющиеся одновременно. |

Обоснование выбора:

1. Унификация: Один инструмент для кода, CI/CD, реестра образов, управления секретами и Wiki. Это снижает затраты на интеграцию и обучение.
   
2. Гибкость: Полная поддержка YAML-шаблонов позволяет создать библиотеку типовых пайплайнов, которые будут переиспользоваться во всех микросервисах.
   
3. Self-Hosted Runners: Критично для микросервисов: вы можете разместить агенты сборки рядом с сервисами (в той же VPC/Private Subnet), ускоряя загрузку образов и повышая безопасность (секреты не уходят в публичную сеть).
   
4. Безопасность: Возможность защитить переменные (Protected) так, что они будут доступны только при сборке для определенной ветки (например, main).
   

## Задача 2: Логи

Предложите решение для обеспечения сбора и анализа логов сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор логов в центральное хранилище со всех хостов, обслуживающих систему;
- минимальные требования к приложениям, сбор логов из stdout;
- гарантированная доставка логов до центрального хранилища;
- обеспечение поиска и фильтрации по записям логов;
- обеспечение пользовательского интерфейса с возможностью предоставления доступа разработчикам для поиска по записям логов;
- возможность дать ссылку на сохранённый поиск по записям логов.

  Предлагаемое решение: Elastic Stack (ELK) — Filebeat + Elasticsearch + Kibana.

  

| Требование | Реализация в Elastic Stack |
| :--- | :--- |
| **Сбор логов в центральное хранилище** | `Filebeat` (легковесный агент) устанавливается на каждый хост и отправляет логи в `Elasticsearch`. |
| **Минимальные требования к приложениям (сбор из stdout)** | Приложения пишут в `stdout`/`stderr`. `Docker`/`Containerd` автоматически собирает их, `Filebeat` читает Docker-логи или системный `journald`. Не нужно ставить SDK или библиотеки. |
| **Гарантированная доставка** | `Filebeat` использует механизм подтверждения (`acknowledgement`) от `Elasticsearch` и имеет внутреннюю очередь. При недоступности кластера сохраняет логи на диске и повторяет отправку. |
| **Поиск и фильтрация** | `Kibana` (`Discover`). Мощный DSL-поиск (`KQL` — Kibana Query Language), фильтры по времени, уровню и названию сервиса (через поля `service.name`, `log.level`). |
| **UI и доступ разработчиков** | `Kibana` — веб-интерфейс. Через пространства (`Spaces`) и роли (`Kibana Roles`) можно дать разработчикам доступ только к их сервисам (фильтрация по индексу). |
| **Ссылка на сохранённый поиск** | В `Kibana` любой поиск можно сохранить как `Saved Search`, скопировать URL-ссылку и отправить коллеге. Ссылка восстанавливает все фильтры и временной диапазон. |

Обоснование выбора:

1. Доминирующий стандарт: ELK — самый популярный Open Source стек для логов. Огромное сообщество, большое количество готовых парсеров и интеграций.

2. Низкий порог входа: Разработчикам достаточно просто писать в stdout в формате JSON (структурированные логи). Filebeat автоматически добавит поля host, container_id, timestamp.

3. Масштабируемость: Elasticsearch легко масштабируется горизонтальноавление нод). Filebeat может работать на тысячах хостов с минимальным потреблением ресурсов (обычно <100MB RAM).

4. Производительность: Поиск по логам занимает миллисекунды благодаря инвертированным индексам Elasticsearch.



## Задача 3: Мониторинг

Предложите решение для обеспечения сбора и анализа состояния хостов и сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор метрик со всех хостов, обслуживающих систему;
- сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network;
- сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network;
- сбор метрик, специфичных для каждого сервиса;
- пользовательский интерфейс с возможностью делать запросы и агрегировать информацию;
- пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы.

Предлагаемое решение: Prometheus + Node Exporter + cAdvisor (или kube-state-metrics) + Grafana.

Это открытый стек, ставший отраслевым стандартом для мониторинга микросервисов.

Взаимодействие компонентов
1. Node Exporter – агент, устанавливаемый на каждый хост (физический или виртуальный).
Собирает метрики OC: CPU, память, диск, сеть.
Отдаёт их в формате Prometheus по адресу http://<host>:9100/metrics.

2. cAdvisor (Container Advisor) – агент для мониторинга контейнеров.
Обычно запускается DaemonSet (в Kubernetes) или рядом с Docker-демоном.
Показывает метрики каждого контейнера: CPU, RAM, сеть, диск, а также специфичные для процессов (например, количество goroutine, открытых файлов).
Endpoint: http://<host>:4194/metrics.

3. Prometheus Server – система сбора и хранения метрик.
Периодически (по расписанию) "забирает" (scrape) метрики с Node Exporter, cAdvisor и с самих приложений (если у них есть /metrics).
Сохраняет данные в собственной TSDB (time series database).
Поддерживает мощный язык запросов PromQL для агрега, фильтрации и вычислений.

4. Grafana – визуализатор.
Подключается к Prometheus (как источник данных).
Позволяет строить дашборды (панели) в реальном времени, создавать графики, таблицы, алерты.
Поддерживает общие дашборды (шаблоны) и систему разграничения доступа (можно дать разработчикам кастомные панели).



Обоснование выбора

1. Открытость и экосистема
Prometheus + Grafana – самые популярные Open Source решения. Поддерживаются почти всеми облачными провайдерами и CI/CD инструментами. Большое количество готовых дашбордов (например, известный "Node Exporter Full" или "Kubernetes Monitoring via Prometheus").

2. Гибкость сбора
Prometheus не требует центрального агента – он pull-модель (сам забирает метрики). Это упрощает масштабирование: вы можете добавлять новые хосты/сервисы, и они автоматически обнаруживаются через Service Discovery (Kubernetes, Consul, file_sd).

3. Мощный язык запросов
PromQL позволяет считать процентили, скользящие средние, выявлять аномалии. Агрегация поейблам (например, по сервису, контейнеру или хосту) даёт гибкость для построения как глобальных, так и детализированных метрик.

4. Независимость от приложений
Системные метрики (CPU, RAM, диск, сеть) собираются без участия разработчиков – достаточно установить Node Exporter и cAdvisor. Специфичные метрики требуют лишь добавить эндпоин /metrics (что тривиально для современных фреймворков).

5. Надёжное хранение
Prometheus TSDB устойчив к сбоям, поддерживает сжатие и долгосрочное хранение. При необходимости можно настроить удалённое хранение (Thanos, VictoriaMetrics) для больших объёмов.

6. Визуализация и алерты
Grafana предоставляет богатый UI, возможность встраивать дашборды, отправлять алерты в Telegram, Slack, PagerDuty (через Grafana Alerting). Разработчики могут самостоятельно создавать дашборды для своих сервисов, не имея доступа к инфраструктурным настройкам Prometheus.
